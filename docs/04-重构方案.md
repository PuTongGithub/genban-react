# genban-react 项目重构方案

## 文档信息

- **创建日期**: 2026-03-01
- **目标版本**: v1.0.0
- **文档状态**: 初稿

---

## 一、重构目标

### 1.1 核心目标

| 目标 | 说明 | 验收标准 |
|------|------|----------|
| 架构清晰化 | 分离关注点，明确各层职责 | 新增功能无需修改现有模块 |
| 状态管理规范化 | 引入轻量级状态管理库 | 跨组件状态共享无需 props drilling |
| 代码可维护性提升 | 消除重复代码，统一规范 | 代码重复率降低 50% 以上 |
| 可测试性增强 | 模块解耦，便于单元测试 | 核心模块测试覆盖率达到 80% |

### 1.2 非目标

- 不引入重型框架（如 Redux、Material-UI）
- 不改变现有 UI 视觉效果
- 不修改后端接口契约
- 不增加新的业务功能

## 二、现状问题分析

### 2.1 架构层面问题

| 问题 | 影响 | 严重程度 |
|------|------|----------|
| `useChat` Hook 过于庞大（300+ 行） | 难以理解和维护 | 🔴 高 |
| API 层与 Hook 层边界模糊 | 职责不清，难以测试 | 🔴 高 |
| 缺乏统一状态管理 | 跨组件通信复杂 | 🟡 中 |
| 重复的错误处理逻辑 | 代码冗余，维护困难 | 🟡 中 |

### 2.2 代码质量问题

| 问题 | 位置 | 示例 |
|------|------|------|
| 重复代码 | `authApi.ts`, `chatApi.ts` | `fetchWithErrorHandling` 方法重复定义 |
| 类型定义不一致 | `types/message.ts` | `StreamData` 与 `Message` 字段命名不统一 |
| Ref 滥用 | `useChat.ts` | 使用 8 个 ref，逻辑难以追踪 |
| 硬编码字符串 | 多处 | 错误消息直接写死在代码中 |

### 2.3 工程化问题

| 问题 | 影响 |
|------|------|
| 无路径别名 | 导入路径冗长，难以重构 |
| 无测试覆盖 | 无法保证重构后功能正确性 |
| 无错误边界 | 组件崩溃导致整个应用白屏 |
| CSS 无模块化 | 样式冲突风险，难以维护 |

## 三、重构阶段规划

### 阶段一：基础架构升级（预计 2-3 天）

#### 3.1.1 引入 Zustand 状态管理

**目标**: 将分散的状态集中到 Store 中管理

**具体任务**:

1. 安装依赖
   ```bash
   npm install zustand
   npm install -D @types/node
   ```

2. 创建 Store 目录结构
   ```
   src/
   └── stores/
       ├── authStore.ts      # 认证状态
       ├── chatStore.ts      # 聊天状态
       └── index.ts
   ```

3. 实现 `authStore`
   - 迁移 `useAuth` 中的状态逻辑
   - 保持 localStorage 持久化能力
   - 提供清晰的 actions: `login`, `logout`, `clearError`

4. 实现 `chatStore`
   - 迁移消息列表状态
   - 迁移连接状态
   - 提供消息操作方法

**验收标准**:
- [ ] `useAuth` 简化为 50 行以内
- [ ] `useChat` 不再直接管理消息数组状态
- [ ] 组件可通过 Store 直接访问状态，无需层层传递

---

#### 3.1.2 重构 API 层

**目标**: 统一 HTTP 客户端，消除重复代码

**具体任务**:

1. 创建统一 HTTP 客户端
   ```typescript
   // src/api/client.ts
   class HttpClient {
     private baseURL: string;
     private defaultHeaders: Record<string, string>;
     
     async request<T>(config: RequestConfig): Promise<T>;
     private handleError(error: unknown): never;
   }
   ```

2. 重构 `authApi`
   - 使用 HttpClient
   - 移除重复的错误处理逻辑
   - 专注于业务接口定义

3. 重构 `chatApi`
   - 分离 HTTP 请求和 SSE 流处理
   - 提取 SSE 处理为独立模块

**验收标准**:
- [ ] `fetchWithErrorHandling` 只在 `client.ts` 中存在一份
- [ ] `authApi` 和 `chatApi` 代码行数减少 30% 以上
- [ ] 新增 API 只需定义接口，无需重复错误处理代码

---

#### 3.1.3 拆分 useChat Hook

**目标**: 单一职责，每个 Hook 只做一件事

**拆分方案**:

| 原 Hook | 拆分后 | 职责 |
|---------|--------|------|
| `useChat` | `useChatMessages` | 消息列表的增删改查 |
| | `useChatConnection` | SSE 连接的生命周期管理 |
| | `useChatRetry` | 重连逻辑的封装 |
| | `useChat` (简化版) | 组合以上 Hooks，提供统一接口 |

**验收标准**:
- [ ] 每个 Hook 不超过 100 行
- [ ] Hooks 之间无循环依赖
- [ ] 现有组件无需修改即可正常工作

---

### 阶段二：工程化改进（预计 1-2 天）

#### 3.2.1 配置路径别名

**目标**: 简化模块导入路径

**具体任务**:

1. 更新 `tsconfig.json`
   ```json
   {
     "compilerOptions": {
       "paths": {
         "@/*": ["./src/*"],
         "@components/*": ["./src/components/*"],
         "@stores/*": ["./src/stores/*"],
         "@hooks/*": ["./src/hooks/*"],
         "@api/*": ["./src/api/*"],
         "@types/*": ["./src/types/*"],
         "@utils/*": ["./src/utils/*"]
       }
     }
   }
   ```

2. 更新 `vite.config.ts`
   ```typescript
   export default defineConfig({
     resolve: {
       alias: {
         '@': path.resolve(__dirname, './src'),
         // ... 其他别名
       }
     }
   });
   ```

3. 批量替换导入语句（使用 IDE 重构功能）

**验收标准**:
- [ ] 所有 `../` 相对路径导入替换为别名导入
- [ ] 项目可正常编译运行
- [ ] 无路径相关错误

---

#### 3.2.2 类型系统重构

**目标**: 统一类型定义，消除不一致

**具体任务**:

1. 统一消息相关类型
   ```typescript
   // src/types/message.ts
   export interface Message {
     id: string;
     role: 'user' | 'assistant' | 'tool';
     content: string;
     reasoningContent?: string;
     toolCalls?: ToolCall[];
     source: MessageSource;
     timestamp: number;
   }
   
   export interface StreamData {
     // 与 Message 字段命名保持一致
     id: string;
     role: 'user' | 'assistant' | 'tool';
     content: string;
     reasoning_content?: string;  // API 返回字段
     tool_calls?: ToolCall[];
     type: MessageSource;
   }
   ```

2. 创建类型转换工具函数
   ```typescript
   // src/utils/transforms.ts
   export function streamDataToMessage(data: StreamData): Message;
   ```

3. 统一 API 错误类型
   ```typescript
   // src/types/error.ts
   export type ErrorCode = 
     | 'NETWORK_ERROR'
     | 'SERVER_ERROR'
     | 'UNAUTHORIZED'
     | 'ABORTED'
     | 'UNKNOWN';
   ```

**验收标准**:
- [ ] 类型定义集中管理，无分散定义
- [ ] API 返回类型与内部使用类型转换清晰
- [ ] 无 `any` 类型使用

---

#### 3.2.3 添加错误边界

**目标**: 防止组件崩溃导致白屏

**具体任务**:

1. 创建错误边界组件
   ```typescript
   // src/components/ErrorBoundary.tsx
   class ErrorBoundary extends React.Component<Props, State> {
     static getDerivedStateFromError(error: Error);
     componentDidCatch(error: Error, errorInfo: ErrorInfo);
     render();
   }
   ```

2. 在应用根组件包裹
   ```tsx
   // App.tsx
   <ErrorBoundary fallback={<ErrorPage />}>
     <App />
   </ErrorBoundary>
   ```

**验收标准**:
- [ ] 组件抛出错误时显示友好的错误页面
- [ ] 错误信息可上报（预留扩展点）
- [ ] 用户可点击重试恢复

### 阶段三：质量保障（预计 2-3 天）

#### 3.3.1 引入测试框架

**目标**: 为核心模块添加单元测试

**具体任务**:

1. 安装依赖
   ```bash
   npm install -D vitest @testing-library/react @testing-library/jest-dom jsdom
   ```

2. 配置 Vitest
   ```typescript
   // vitest.config.ts
   export default defineConfig({
     test: {
       environment: 'jsdom',
       globals: true,
       setupFiles: './src/test/setup.ts'
     }
   });
   ```

3. 编写测试用例（优先级）
   - [ ] `authStore` - 登录、登出、状态持久化
   - [ ] `chatStore` - 消息增删、状态变更
   - [ ] `HttpClient` - 请求拦截、错误处理
   - [ ] `useChatMessages` - 消息操作逻辑

**验收标准**:
- [ ] Store 模块测试覆盖率 > 80%
- [ ] API 客户端核心逻辑测试覆盖
- [ ] CI 中可运行测试

---

#### 3.3.2 代码规范强化

**目标**: 统一代码风格，减少低级错误

**具体任务**:

1. 更新 ESLint 配置
   ```javascript
   // eslint.config.js
   export default [
     // 现有配置...
     {
       rules: {
         'no-console': ['warn', { allow: ['error'] }],
         '@typescript-eslint/explicit-function-return-type': 'warn',
         'no-duplicate-imports': 'error'
       }
     }
   ];
   ```

2. 添加 Prettier（如需要）
   ```bash
   npm install -D prettier eslint-config-prettier
   ```

3. 配置 Git Hooks（可选）
   ```bash
   npm install -D husky lint-staged
   ```

**验收标准**:
- [ ] `npm run lint` 无警告
- [ ] 提交前自动检查代码规范

### 阶段四：优化增强（可选，预计 3-5 天）

#### 3.4.1 引入 Tailwind CSS

**目标**: 原子化 CSS，提升样式开发效率

**具体任务**:

1. 安装配置
   ```bash
   npm install -D tailwindcss postcss autoprefixer
   npx tailwindcss init -p
   ```

2. 逐步替换 CSS 文件
   - 先替换通用样式（布局、间距、颜色）
   - 保留组件特有复杂样式

**验收标准**:
- [ ] 基础样式使用 Tailwind 实现
- [ ] 无样式冲突
- [ ] 构建产物体积不显著增加

---

#### 3.4.2 功能增强

| 功能 | 实现方案 | 优先级 |
|------|----------|--------|
| 暗黑模式 | CSS 变量 + localStorage | 低 |

| 输入草稿保存 | localStorage 自动保存 | 低 |

## 五、风险评估与回滚方案

### 5.1 风险识别

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|----------|
| 重构引入 Bug | 中 | 高 | 每阶段完成后全面测试 |
| 进度延期 | 中 | 中 | 预留 20% 缓冲时间 |
| 团队成员不熟悉新方案 | 低 | 中 | 重构前技术分享 |

### 5.2 回滚策略

1. **代码层面**
   - 每个阶段独立分支开发
   - 阶段完成后合并到 main
   - 保留重构前标签 `v0.x-before-refactor`

2. **数据层面**
   - localStorage 数据格式保持兼容
   - 新增字段使用可选类型
